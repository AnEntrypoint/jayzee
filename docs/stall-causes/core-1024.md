# 1024-tier stalls: shared-core and clock causes (Phase B)

Result: the cause is still open. The shared-core explanation is not supported, the clock-clustering test had no power, and the stall frames are too few to separate the arms.

## Run

- Matrix: job core-matrix-2, output in build/diag/core (git-ignored). Nine PAUSED runs, three rounds of core-shared, core-separate and core-none, in round order.
- Pause and resume: foreign CPU-heavy pids are paused by PID with SIGSTOP and resumed with SIGCONT, in a finally block. Each attempt re-selects its foreign set with ps (pcpu at least 15), excluding claude, hyperagent, gm-core, playwriter, Xvfb, selkies, chromium and any cwd under /workspace/jayzee. Busy share after pausing was 4.2% to 16.7%. The 0.2 gate refused three attempts (exit 2), each retried with a fresh set, and all nine runs then passed.
- Attempt 1 (build/diag/core-attempt1-browser-down) produced no data. The project playwriter browser had stopped answering on debug port 10221, so every run ended with a page error. None of it is counted. The browser was restarted through the playwriter verb, and the debug port was checked with curl before attempt 2.
- Placement: the renderer main threads of this profile are pinned to cpu 0 in every arm, which is core 0 with SMT sibling cpu 1.
  - core-shared: LIVE samplers and the co-tenant burn both on cpu 1, the renderer's SMT sibling.
  - core-separate: samplers on cpu 2 (core 1), co-tenant on cpu 4 (core 2).
  - core-none: samplers on cpu 2, no co-tenant. This is the control.
- Clock: each run records the clock source, and each CPU's governor and scaling_cur_freq, at start and end. The renderer's CPU and frequency are sampled every 100 ms.
- Each run produced 540 frames. The page is a timed run, so it ends on its frame count and the 120 s sampler duration is only a ceiling.

## What the numbers say

- Shared core: the verdict is "not supported". The arm that shares the renderer's physical core with the sampler and the co-tenant has fewer stall frames than the separate-core arm, and both are far below the no-co-tenant control. Stall frames do not rise with co-tenant placement in this run.
- The shared-core arm has a higher median frame, 61.7 to 63.1 ms, against 47.0 to 50.1 ms in core-separate and 47.6 to 53.1 ms in core-none. This is a steady shift in every round, and it is not a stall count. It is a separate observation, not a stall cause.
- Clock clustering: the test has no power here. The renderer's frequency changed sample to sample in 324 to 434 places per run, about every 65 ms. Every frame window of about 50 ms therefore has a change within the 100 ms pad, so framesNear equals the frame count in every run. The stall share near a change then equals 1 by construction, and the "does not cluster" verdict follows from that, not from a measurement. C1 is recorded as uninformative, not as held.
- Clock at stalls: all four runs with stalls read a lower stall-time frequency, by 0.03% (core-shared round 2, one stall), 5.5% (core-separate round 3), 6.5% (core-none round 1) and 7.0% (core-none round 3). Three of the four are a few percent, which is a real difference in size but rests on two to ten stall frames per run. It does not establish a cause.
- The control's round-1 concentration (10 stalls) repeats the earlier pinned run r1-P (12 stalls, same round). It shows up with and without a co-tenant, so it is not explained by co-tenant placement.

## Decision

- The cause is still open. Shared-core is not supported (S1 failed). Clock clustering could not be tested with this sampling (C1 uninformative). The clock-at-stall difference (C2) is real in direction but small, and it rests on very few stalls.
- No fix is adopted from these runs. Pinning and placement are not changed.
- To settle it: a sampling rate or a change threshold that yields fewer frequency changes (for example, counting only moves of at least 5%), and enough stall frames per arm to separate them. Neither is in this commit.

## Harness defects found in this run

- pinApplied was false in five of nine runs. A renderer that had exited before the end-of-run read has an empty readback, and the old check counted it as a failure. Fixed in controlled-run.mjs by pinOutcome, which ignores renderers not alive at the end (gate "pinOutcome reads the readback ..."). The stored run.json values are unchanged. Recomputed from each stored pinned list, the fixed value is:
  [["core-none-r1",false,true],["core-none-r2",false,true],["core-none-r3",true,true],["core-separate-r1",true,true],["core-separate-r2",false,true],["core-separate-r3",true,true],["core-shared-r1",false,true],["core-shared-r2",true,true],["core-shared-r3",false,true]]
- Every renderer of the profile is pinned, not only the page's renderer. The idle renderers sit on cpu 0 with the main thread, which adds no measured load. Recorded, not changed.
- The frequency-change test is saturated (see above), so its verdict is not evidence.
- The first pass of analyseRunData's window read startMs from offCpuForStalls, which does not carry it. The window now comes from the probe's stalls (gate "analyseRunData counts the one stall ...").
